---
name: Daily Submission Word report policy
description: Customer Word layout, saved-baseline semantics and shared Daily PDF downloads.
---

Daily Submission landing-row Download and individual report Download must produce the same PDF based on the supplied daily document-governance Word layout. Preserve its section order, colours, tables and change indicators. Unmatched fields must read exactly “To be mapped”.

**Why:** The user explicitly required the Word design and identical downloads at both entry points. The attachment contains illustrative identities, numbers and a reviewer-only appendix, none of which belong in issued reports.

**How to apply:** Populate actual saved report data and the report's saved previous-submission baseline, not a newly queried baseline that could change historical results. The form's absent previous counts start at zero; absent current input is not permission to copy sample numbers. Match revisions by document category and normalized revision name. Use configured project-team names and actual preparation/submission identity, never a presumed Document Controller title or signature. Remove sample-data headers and reviewer instructions from issued output. Retain explicit zero values, conditional first-report notices and all repeated revision rows. Calibri is not bundled in the supplied file; embed the compatible Carlito fonts and disclose the substitution.

The separate Daily Dashboard PDF follows the customer's four-page presentation and accompanying mapping workbook. It supplements, rather than replaces, the Word-layout daily report. Both exports must retain the saved-baseline semantics above.

**Why:** The user requested separate Report PDF and Dashboard PDF actions. The workbook's matching sample numbers are illustrative, not new validation rules.

**How to apply:** Do not force document-type counts to equal discipline totals, or discipline Under Review counts to equal the pending-review workspace. The dashboard's Overall Under Review counts only the Under Review status across parties, while pending totals and ageing include every review status. Do not silently clamp negative corrections into positive doughnut segments.

Revision percentages use the cumulative total of the revision's own document category: Drawing revisions divide by all Drawings; Submittal revisions divide by all Submittals. Never use the combined total for a revision row.

**Why:** The user explicitly replaced the original combined-denominator rule for the Daily Submission revision section.

**How to apply:** Keep the entry form, daily report PDF and dashboard revision charts consistent. Use all statuses within the matching category's total, not only approved documents. A zero matching-category total yields 0.0%, regardless of the other category's total.

Daily report sign-off keeps Prepared by and Submitted on, removes the entire
Report ID tile, and adds completed intermediate approvals as Reviewed by/on in
ascending action-date order, followed by the actual final Approved by/on.
Use the current Daily submission cycle and organization-local approval times;
assigned reviewers and old sent-back cycles must not certify the current report.

**Why:** The business requested the same reviewer/final-approver distinction as
the Monthly Report for every generated Daily Submission report.

**How to apply:** Keep downloads and newly generated email report attachments on
the shared Daily report layout. Never fabricate missing legacy approval evidence.
Leave workflow routing and already frozen email attachments unchanged.

Daily report and dashboard PDFs share the current-cycle sign-off evidence:
Prepared by/Submitted on, chronological Reviewed by/on, then actual final
Approved by/on. Include available signer-profile images under names, matched
by user ID within the report organization, never by display name. The dashboard
adds a separate landscape sign-off page without replacing its chart pages.

**Why:** The business explicitly requested signatures and equivalent sign-off
details for both Daily downloads and their email attachments. This request uses
attached user-profile signatures; it does not define immutable historical
signature snapshots like the separate CAR policy.

**How to apply:** Preserve missing-signature gaps without invented images.
Use the exact report approval-cycle rules for the dashboard too. Profile images
are read at generation time, so replacing a profile signature affects future
exports; do not describe these images as historically frozen evidence.
